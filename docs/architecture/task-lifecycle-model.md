# Task lifecycle model-check suite

## Entry point and evidence boundary

Run [`pnpm lifecycle:model-check`](../../package.json:16) from the workspace root. The unchanged umbrella runs four entry points: [`check-task-lifecycle.ts`](../../scripts/check-task-lifecycle.ts), [`check-task-store-concurrency.ts`](../../scripts/check-task-store-concurrency.ts), [`check-task-cleanup-protocol.ts`](../../scripts/check-task-cleanup-protocol.ts), and the [parser runner](../../scripts/run-native-tool-call-parser-scoping.mjs). The lifecycle entry point also invokes [`checkExecutionProtocol()`](../../scripts/check-task-execution-protocol.ts:850); no extra package script is required.

**These are bounded safety checks, not a claim that the overall LoopIssue fix is fully validated.** The stage-2 model work covers the ownership, explicit recovery and delegated-completion contracts. It does not establish eventual completion, fairness, physical multi-file atomicity, filesystem lock correctness, cancellation of already-issued external effects, or safety with an older nonparticipating binary. At the end of that backend stage, validation passed 65 focused files / 1,390 tests plus 34 schema tests; UI, extension-host E2E, installed-artifact qualification and full repository validation were still incomplete. Those historical focused results do not establish full-workspace validation of the final candidate.

The checkers call production pure reducers and guards rather than copying their policy. Their environment adapters still abstract locks, write success/failure, approval scope and logical transcript effects. Command orchestration does **not** combine state spaces: graph, containment, execution protocol, shared store, cleanup and parser scopes remain separate bounded explorations. Shared fixture construction is not an executable cross-model refinement proof. Add a joint product only with an explicit production boundary mapping and genuinely cross-model invariants.

## Current production contract

### Persisted ownership is separate from task status

The [history schema](../../packages/types/src/history.ts:203) preserves optional, versioned ownership, delegation, completion and provenance records. [`ExecutionOwner`](../../packages/types/src/history.ts:40) identifies host session, provider, runtime, process and machine evidence. [`ExecutionToken`](../../packages/types/src/history.ts:49) binds that owner to one task and execution generation. [`ExecutionClaim`](../../packages/types/src/history.ts:61) distinguishes active, suspended and settled ownership and records pending cleanup. The lifecycle revision detects graph/action changes independently of execution generation.

- [`claimNewExecution()`](../../src/core/task-persistence/taskLifecycle.ts:406) supplies the first claim only for an exclusively reserved **new** task. [`TaskHistoryStore.claimNewTask()`](../../src/core/task-persistence/TaskHistoryStore.ts:310) refuses existing histories and uncertain preexisting directories. Reading history never adopts its token.
- [`assertExecutionToken()`](../../src/core/task-persistence/taskLifecycle.ts:349) checks exact task, full owner identity and generation. [`assertExecutionAllowed()`](../../src/core/task-persistence/taskLifecycle.ts:375) additionally checks cleanup, execution phase, status, recovery gates, completion prefixes and upstream ownership. Status alone is never launch authority.
- [`interruptExecution()`](../../src/core/task-persistence/taskLifecycle.ts:429) advances the generation immediately and retains suspended cleanup authority. A delegated ancestor stays delegated; interruption is not abandonment.
- [`settleExecution()`](../../src/core/task-persistence/taskLifecycle.ts:444) requires confirmed cleanup and fences again before releasing the claim. A suspended claim is not proof of cleanup. Ordinary disposal is not settlement.
- [`transferExecution()`](../../src/core/task-persistence/taskLifecycle.ts:460) requires the **exact outgoing token** and confirmed cleanup, advances generation/revision and installs the new owner. An active, unblocked status can remain executable; interrupted/delegated work remains suspended until its separate authorization. Completed tasks refuse transfer. The store's [`assertLocalOrSettledOwner()`](../../src/core/task-persistence/TaskHistoryStore.ts:225) accepts a caller's cleanup attestation only for its own local runtime; a peer requires durable settlement, not a claimed boolean or uncommitted death observation.
- [`TaskHistoryStore.saveExecutionSnapshot()`](../../src/core/task-persistence/TaskHistoryStore.ts:388) captures inputs before queueing and checks authority under the storage lock through history writes. Provider-captured final snapshots use the exact fenced cleanup token; stale runtime callbacks do not borrow that token. [`mergeTaskMessageMetadata()`](../../src/core/task-persistence/taskStoreConcurrency.ts:23) and [`mergeHistoryDelta()`](../../src/core/task-persistence/taskStoreConcurrency.ts:46) protect lifecycle, lineage, authority, receipts and provenance from ordinary metadata snapshots.

Fencing prevents future admission/commit; it cannot undo a process, command or request already launched. Transfer must not be used to hide uncertain outgoing cleanup.

### Explicit recovery and preserved failure identity

[`recoverTaskExecution()`](../../src/core/task-persistence/taskLifecycle.ts:685) is the **only interrupted-to-active edge**. The [ordinary transition whitelist](../../src/core/task-persistence/taskLifecycle.ts:25) still rejects interrupted-to-active and interrupted-to-delegated. [`recoveryScope()`](../../src/core/task-persistence/taskLifecycle.ts:576) captures task, revision, generation, claim, exact pending action, blocked action, parent identity and the parent's revision, generation, claim, status, pointers and creating receipt. Recovery requires explicit user-resume intent, exact scope equality, valid new owner identity and a currently eligible choice from [`previewTaskRecovery()`](../../src/core/task-persistence/taskLifecycle.ts:629).

| Choice             | Current meaning                                                                                                                                                                                                                                                                                                                      |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Linked resume      | A cleaned, settled interrupted child becomes active only while its parent retains the exact committed handoff and is not actively executing. The parent's pointers remain unchanged. The resumed child may later create its own child through ordinary guarded admission.                                                            |
| Independent resume | A cleaned, settled interrupted task with no current owning handoff clears live parent/root linkage and retains prior lineage as provenance. It does not restore an ancestor's pointer. Missing/non-owning parent permits this only after explicit recovery; a parent still awaiting the child with contradictory metadata blocks it. |
| Retain delegation  | A settled delegated parent may explicitly continue while its exact awaited child is interrupted and settled. It keeps that handoff and can subsequently replace the interrupted child through normal admission. It cannot silently replace a live descendant.                                                                        |

Prepared/uncertain create actions remain blocked. Failed/denied actions require durable result repair before recovery. [`reconcileDelegationResult()`](../../src/core/task-persistence/taskLifecycle.ts:297) clears only matching pending intent and marks its result written; it does **not** clear the recovery gate. Explicit recovery can remove that gate but preserves terminal receipts and original results. [`assertDelegationAdmission()`](../../src/core/task-persistence/taskLifecycle.ts:158) continues to reject reuse of the original failed action ID: later work needs a new intent.

[`ClineProvider.previewTaskRecovery()`](../../src/core/webview/ClineProvider.ts:4737) retains the full immutable scope and sends only a presentation/prompt identity. [`ClineProvider.recoverTask()`](../../src/core/webview/ClineProvider.ts:4800) validates prompt, task, choice and current view before store admission; the store rechecks the provider's scope predicate at the actual write boundary. Duplicate/stale decisions cannot authorize another incarnation. Navigation, hydration, queued feedback and subtask auto-approval are not explicit recovery.

[`TaskScheduler.schedule()`](../../src/core/task/TaskScheduler.ts:33) deduplicates task/generation/owner scheduling. [`TaskScheduler.admit()`](../../src/core/task/TaskScheduler.ts:50) guards before and after permit acquisition. Model scheduler actions test this production guard, not actual semaphore fairness, permit counts or end-to-end scheduling.

### Observer initialization and conservative restart limits

[`TaskHistoryStore.initialize()`](../../src/core/task-persistence/TaskHistoryStore.ts:174) discovers records, quarantines legacy repair journals, checks confirmed-dead owners, then starts observation. It no longer assumes that an active child is an orphan merely because another provider/store starts. [`repairConfirmedDeadOwners()`](../../src/core/task-persistence/TaskHistoryStore.ts:716) obtains fresh history and parent state under the storage lock and invokes [`repairDeadExecution()`](../../src/core/task-persistence/taskLifecycle.ts:487) only after positive death proof. Repair fences and settles the owner, changes an active leaf to interrupted, and retains nested delegated ancestors, links and receipts. It does not schedule work.

[`probeExecutionOwner()`](../../src/core/task-persistence/executionHost.ts:39) is deliberately conservative:

1. Explicit settled metadata is settlement evidence.
2. The same loaded host-session nonce remains live, including suspended ancestors, queued work and cleanup. Absence from one provider's registry does not prove death.
3. Another session can be proven dead only when **both** sides have trusted local-machine proof, machine identities match, the PID is not the current process, and the process probe positively proves absence. A present/reused PID, a denied/failed probe or ambiguous machine yields unknown, not takeover permission.
4. No timestamp, heartbeat age, focus state or advisory-lock timeout proves execution-owner death.

**Stage-2 default machine proof is unknown.** [`createExecutionHost()`](../../src/core/task-persistence/executionHost.ts:18) uses hostname only diagnostically unless an OS-backed local identity is explicitly supplied. The deterministic model's trusted-machine/dead-process branch uses injected evidence; it does not prove default cross-process automatic repair is available.

Ownerless legacy and unknown-version histories remain inspectable but unclaimed. There is no implicit legacy adoption, mass activation or active-parent normalization. The low-level [`completeDelegatedChild()`](../../src/core/task-persistence/taskLifecycle.ts:86) still contains its historical active-parent/interrupted-child compatibility behavior, but **it is not the claimed runtime completion authority**. The strict path requires [`hasExactDelegation()`](../../src/core/task-persistence/taskLifecycle.ts:514), including delegated parent status and one matching committed creating receipt. A contradictory active parent still awaiting the child is not silently normalized. [`quarantineLegacyRepair()`](../../src/core/task-persistence/TaskHistoryStore.ts:704) preserves old journals under quarantine rather than replaying ownerless targets into a live graph.

### Storage coordination and completion ordering

[`TaskHistoryStore.withLock()`](../../src/core/task-persistence/TaskHistoryStore.ts:1598) serializes all participating store queue turns through a canonical-storage advisory lock. Lock order is **local queue turn → canonical storage lock → per-file lock**. Locked callbacks must not reenter the store. No human approval, runtime teardown, stream or scheduler wait belongs under this lock.

[`TaskHistoryStore.lifecycleCommand()`](../../src/core/task-persistence/TaskHistoryStore.ts:767) reads fresh records and related lineage. [`persistLifecycle()`](../../src/core/task-persistence/TaskHistoryStore.ts:264) compares the complete expected record under the atomic per-file writer and synchronously rechecks scope after asynchronous path/lock/read work. Read-back distinguishes confirmed unchanged, committed-after-error and uncertain outcomes. Post-commit notification failure is not permission to roll back durable success. Ordinary cache-relative metadata deltas remain a different API; claimed lifecycle fields cannot be changed through them.

[`TaskHistoryStore.completeDelegatedTask()`](../../src/core/task-persistence/TaskHistoryStore.ts:560) captures the request before queueing and holds the storage lock across:

1. **Fresh validation before any transcript effect.** [`validateDelegatedCompletion()`](../../src/core/task-persistence/taskLifecycle.ts:737) checks full child/parent tokens, both revisions, strict handoff, exact creating receipt, exact pending finish intent and the parent's upstream owner. The store separately checks local child authority and local-or-settled parent ownership. Compatible committed duplicates return without a new result; an existing prepared operation requests repair rather than blind replay.
2. Read-only preflight of both parent histories. [`readApiMessagesForCompletion()`](../../src/core/task-persistence/apiMessages.ts:251) does not migrate/write legacy history before authority. Missing, invalid or conflicting histories refuse rather than becoming empty replacement histories.
3. **Durable parent prepared receipt**, via [`prepareDelegatedCompletion()`](../../src/core/task-persistence/taskLifecycle.ts:782), with the final current-scope check. This receipt is the write-ahead record, not a second journal store. It gates both participants before transcript mutation.
4. Exact API result, then stable-identity UI result. [`withDelegationCompletion()`](../../src/core/task-persistence/apiMessages.ts:259) selects the actual creating tool call, not the latest tool by name, and refuses conflicting existing results. [`finishCompletionPrefix()`](../../src/core/task-persistence/TaskHistoryStore.ts:668) writes histories before completion metadata.
5. **Child completion first, parent completion last**, using [`commitDelegatedCompletion()`](../../src/core/task-persistence/taskLifecycle.ts:874). Child generation advances and cleanup remains pending. Parent pointers clear and its receipt becomes committed, but the parent claim is not activated by this reducer.

Scope revocation before the prepared write causes no completion effect. After a durable prepared receipt, that exact operation may finish even if focus changes; cancellation serializes behind it. If a write fails, prepared-only, API-only, API/UI and child-completed/parent-pending prefixes remain nonexecuting through [`assertNoCompletionPrefix()`](../../src/core/task-persistence/taskLifecycle.ts:363). [`repairDelegatedCompletion()`](../../src/core/task-persistence/TaskHistoryStore.ts:639) validates exact compatible state through [`validateCompletionPrefix()`](../../src/core/task-persistence/taskLifecycle.ts:800), requires local ownership or positive peer death/settlement, and replays stable result/child writes idempotently before the parent commit. Conflicting prefixes are not overwritten. Repair is not execution authorization.

[`ClineProvider.reopenParentFromDelegation()`](../../src/core/webview/ClineProvider.ts:5339) finishes child snapshot/cleanup and settlement before emitting completion and conditionally transfers the parent's exact retained/settled claim for continuation. Restoring parent status to active is not itself permission to launch. Notification/event delivery and physical crash durability are not proved by these reducer models.

[`abandonExecutionDelegation()`](../../src/core/task-persistence/taskLifecycle.ts:527) instead requires exact parent/child authority, settled child cleanup and no owned descendant. [`abandonTaskDelegation()`](../../src/core/task-persistence/TaskHistoryStore.ts:601) writes the nonexecuting parent first, detached child second. A second-write failure can retain old lineage on a settled interrupted child; explicit independent recovery can detach it without reattaching or losing provenance. This is not a physically atomic pair write.

### Preserved graph and containment checks

The graph retains delegate, interrupt, complete and abandon actions; coherent delegated pointers, awaited-child existence/backlink/history, no nondelegated pointers, live-linked ownership, acyclic lineage and immutable completed records. Its two landmarks remain interrupted-child re-delegation and nested delegation. Representative refusals retain concurrent active-child delegation, stale completion after replacement/abandonment, and nested/interrupted completion. This low-level structural graph intentionally does not claim that legacy completion compatibility authorizes modern runtime execution.

Containment retains reserve/refuse, interrupt/owner-change, paused allocation, commit/refusal, fail/uncertain, duplicate/schedule, blocked restore/reload and result repair. All six original landmarks remain: interrupted-parent refusal; failed-restored-reloaded; owner-change-at-commit; duplicate-after-commit; prepared-reload-blocked; uncertain-reload-blocked. The seventh requires **failed-result-repaired-still-blocked**. The model now passes the current failed receipt to result reconciliation, matching its production exact-receipt check; passing the old prepared receipt had become an inert no-op. No production change was needed.

### Ownership/recovery product

Six recovery seeds cover independent (175 states), linked (175), detached (98), parent-first abandonment prefix (98), failed-result (200) and retained delegation (175). Their 921 states are separate from the 101-state completion/approval seed, not one joint state space.

Recovery bounds allow one interruption, one host-death observation/repair, one settled transfer, two cleanup settlements, one captured recovery decision and at most one successful recovery. Observer and scheduler checks are repeatable self-edges; they cannot create authority. The [explorer](../../scripts/check-task-execution-protocol.ts:201) checks every edge, including deduplicated refusals, and fails on an unseen depth-frontier successor or state-budget overflow. Counterexamples include the shortest breadth-first prefix and intermediate states. Completion permits one crash/fault, owner replacement, same-ID finish replacement and scope revocation; it captures approval, validates under the lock, permits revocation during read-only preflight, then writes/repairs the prepared, API, UI, child and parent stages. Repair starts from the receipt and replays already-durable effects to check idempotence, rather than skipping directly to the unfinished step.

The 20 invariant groups cover bounded valid claims; operation-specific activation; no blocked scheduler admission; stale execution/mutation callbacks; nonmutating observers; immutable failed receipt/result identity; unusable original failed ID; metadata protection; exact linked ownership/independent provenance; effect-free stale/duplicate recovery; cleanup authority; monotonic revisions/generations; authoritative completion approval; ordered prefixes; gating of both participants; compatible idempotent repair; no duplicate/refused transcript effect; cancellation ordering; exact result routing; and nonexecuting parent/fenced child completion.

All **18 explored landmarks** are required:

- explicit linked resume; explicit independent resume; retained interrupted descendant; settled owner transfer;
- known-dead repair; failed result repaired before resume; cancelled recovery approval; detached provenance retained;
- cancel-before-prepare refusal; cancel-after-prepare commit; owner-change approval refusal; intent-change approval refusal;
- prepared/API/UI/child prefix repair; parent committed prefix; scope revoked at the write boundary.

The **seven deterministic representative landmarks** call production reducers/probes for: dead nested chain retained and unwound; dead-owner completion-prefix repair without launch; explicitly resumed interrupted middle task delegating a new leaf; legacy/unknown/contradictory active-parent inspection only; unknown default machine proof; strict completion/conflicting-prefix refusal; and full recovery parent/task/action-scope refusal. These are representative safety scenarios, not exhaustive nested interleavings or an eventual-unwind proof.

### Shared-store mapping and promoted witnesses

The shared-store model retains independent caches, explicit refresh, local/storage/file mutexes, per-file revalidation/commit and failure prefixes. Ordinary metadata scenarios call production [`computeHistoryDelta()`](../../src/core/task-persistence/taskStoreConcurrency.ts:17) and [`mergeHistoryDelta()`](../../src/core/task-persistence/taskStoreConcurrency.ts:46). Completion uses a captured immutable request but fresh disk validation under the storage mutex, then a prepared parent receipt, logical transcript effect and child/parent compare-and-set writes. Claimed writes are not ordinary cache-relative deltas.

The competitor remains the original causal **replacement scenario**: settle the old child/parent, explicitly recover the parent retaining delegation, then reserve/claim/commit the replacement using production reducer endpoints. This is a composite environment action with condensed preparation, not a claim that production performs all replacement work under one physical transaction. Its allocation prefix is nonexecuting and must fail the production execution guard. More detailed ownership/recovery prefixes are checked separately, without claiming a cross-model product proof.

The six retained scenarios have 31 states (peer-field merge), 4 (status rejection), 13 (completion's second lifecycle-write failure), 35 (distinct-task writes), 38 (stale completion ownership), and 66 (stale-save detachment). All original phases remain, plus transcript. All original landmarks remain: stale cache/newer disk, first lifecycle commit/second pending, and first lifecycle commit/second failed. Completion now has a **preceding prepared-parent write**; the pair-prefix landmarks count the child and final parent lifecycle commits after that receipt, matching the new ordering instead of deleting the failure scenario.

**[#1469](https://github.com/Zoo-Code-Org/Zoo-Code/issues/1469) is promoted to a universal invariant.** Every explored state checks that an old completion cannot clear a committed newer handoff or leave its active linked child orphaned. Logical result effects must have a validated, durable prepared receipt for the exact parent/child/creating action. A refused completion has no transcript or lifecycle commits. The [reviewed causal schedule](../../scripts/check-task-store-concurrency.ts:805) remains an explicit replay and named fourth landmark:

1. Capture the old child's completion request.
2. The competing host reads/prepares, commits the old child's settlement, commits the paused replacement, then commits the parent's newer handoff.
3. The old completion enters preparation under the storage lock and validates fresh authority.
4. It **refuses before receipt/transcript mutation**. The former child-write/parent-clearing suffix is disabled; the replacement handoff survives.

The substantive property is no longer an expected failure. **[#1021](https://github.com/Zoo-Code-Org/Zoo-Code/issues/1021) remains universal**: stale message metadata cannot restore detached parent/root links, including the refreshed-cache schedule. Neither scenario nor its original safety requirement was dropped. There are **no retained expected-unsafe witnesses** in this current bounded shared-store domain; this is not a statement that all possible production races are absent.

The 12 shared-store invariants cover host/storage/file mutex ownership, protected detachment, absent-delta field preservation, child-history union, pair order, whole-delta rejection, old-completion/new-handoff safety, authority-before-transcript/refusal purity, receipt/transcript/child/parent order, and no claimed live orphan outside a provably nonexecuting allocation prefix.

## Validation and extension guidance

- The full [`pnpm lifecycle:model-check`](../../package.json:16) umbrella passed with the counts above. Strict direct TypeScript checking of the three edited model scripts passed using [`tsc --noEmit --target ES2022 --module NodeNext --moduleResolution NodeNext --esModuleInterop --skipLibCheck --strict`](../../scripts/check-task-execution-protocol.ts:1), followed by their three relative script paths. This checks model/source types, not repository-wide runtime integration.
- An additional unused-local/parameter diagnostic run reported an existing unused type assertion in [`experiment.ts`](../../packages/types/src/experiment.ts:35). No unrelated source/configuration was changed.
- The required extension ESLint invocation with suppression pruning reported all three scripts **ignored outside its base path**, exit 1 under zero-warning policy. This is a lint coverage blocker, not a lint pass. No lint disabling, configuration bypass or new suppression was added. Formatting and diff-whitespace checks are separate checks.
- Node 22.22.2 differs from the requested 22.23.1 engine; the existing formatter also warns about its unsupported ignore option. Neither warning is a model proof assumption.
- Final backend/schema selection, extension/shared-types/webview type checks, touched-source lint and the model umbrella passed. Model scripts remain outside the extension ESLint base path. UI tests, E2E, full repository tests and packaging were deliberately deferred; no staged/committed work, changelog or changeset was produced.

Keep pure lifecycle policy in [`taskLifecycle.ts`](../../src/core/task-persistence/taskLifecycle.ts), and update the narrowest applicable model/action/invariant in the same change. Preserve named causal scenarios and refusal coverage. Never report budget/depth truncation as success or weaken an assertion merely to turn a counterexample green. Diagnose a production defect before changing a specification; put a regression at the lowest test layer capable of expressing it. Use real-file integration for persistence boundaries and extension-host tests for restart, view messaging, delayed streams or actual scheduler/cleanup boundaries, not to duplicate reducer permutations.

The executable TypeScript approach provides deterministic bounded state enumeration while directly calling production transitions. For unbounded temporal guarantees, fairness, richer relational ownership or protocol refinement, evaluate TLA+/PlusCal, Quint/TLC or Alloy with explicit assumptions and a production trace adapter. See the [TLA+ high-level view](https://lamport.azurewebsites.net/tla/high-level-view.html), [Quint model checking](https://quint-lang.org/docs/model-checkers), [Quint implementation connection](https://quint-lang.org/docs/model-based-testing) and [Alloy bounded scope tutorial](https://alloytools.org/tutorials/online/maintext-FS-1.html). Shared command execution, finite successful recovery examples and advisory locking are not substitutes for those proofs.
